# Feature Specification: P3 引擎漂移修复——2.1.296 工具结果形状容忍与重钉

**Change**: `003-p3-2-1-296`

**Created**: 2026-10-10

**Status**: Draft

**Input**: User description: "遗留（P3 路由，已记录在台账与 report.md）：第一项 = claude 2.1.296 解码器两形状容忍 + engine.lock 重钉 + 真实复冒烟（临时缓解：本机 CLI 降回 2.1.291）；其后为 T11-① 单飞清理、T5-① 16MB 隔离等 hardening 清单"——本次只做第一项，其余项留待后续变更集（见 Out of Scope）。

## 背景（问题陈述）

P2 验收的真实引擎冒烟（2026-10-10，本机 claude 2.1.296）暴露一个**引擎漂移**缺陷：

- 仓库 pin 的引擎版本是 2.1.291（`engine.lock`），而本机实际 CLI 已升到 2.1.296；
- 2.1.296 把工具结果回流事件（`user` 事件的 `message.content[].content`）从**字符串**改为**文本块数组**；
- mulix 的流解码器按 2.1.291 的字符串形状建模，遇到数组形状即判定「stdout 流损坏」，整条回合 fail-closed 收口（回合 error → 子代理级联收口 → 进程 exit 1）。

后果：凡是经过 MCP 工具成功回流的回合（子代理委派 `spawn`、外部工具 `echo` 往返）都会在结果回流那一刻断流；P2 的「真实子代理委派闭环」只能靠自动化测试与部分真实验证支撑，`report.md` 记了一条「诚实限制」。当前用户侧的唯一缓解是**把本机 CLI 降回 2.1.291**——这是把治理 pin 倒过来迁就工具链，不是修复。

同时该缺陷暴露了治理层面的两个空白：

1. **pin 落后于现实**：`engine.lock` 停在 2.1.291，2.1.296 的新形状没有任何 fixture 样本，升级（或上游自动升级）后只能靠真实冒烟才发现断流；
2. **基准未回填**：`engine.lock` 的缓存基准位（`baseline.cache_hit_rate`）自 P1 起就是占位值，P3 起要求重钉时一并回填。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 使用新版引擎跑通委派与外部工具回合 (Priority: P1)

用户的本机 claude CLI 升到了比仓库 pin 更新的版本（如 2.1.296）。升级后用户完成 pin 的更新，随后在 mulix 会话里委派一个子代理任务、并调用一次外部 MCP 工具：两条回合都能跑完——工具结果回流被正确解读、子代理结果与 usage 回收进主会话、进程正常收口。用户不需要手动降级 CLI，也不需要 `--allow-engine-drift` 这类临时放行开关。

**Why this priority**: 这是 P3 路由的第一项，也是 P2 遗留的唯一「限制」条目的关闭条件；不修复则每次上游小版本升级都可能让委派链断流，而用户侧只能降级或放行漂移。

**Independent Test**: 在本机安装 pin 所指版本的真实 CLI，用一个独立 git 工作区跑一次真实委派 + 一次真实外部工具回合，观察回合完成、结果回收、退出码正常，且会话镜像里能看到工具结果事件与委派链。

**Acceptance Scenarios**:

1. **Given** 引擎回流的工具结果内容是字符串（旧形状），**When** 会话读到该事件，**Then** 结果被正常解读，回合继续（与 P1/P2 行为一致，无回归）。
2. **Given** 引擎回流的工具结果内容是文本块数组（新形状），**When** 会话读到该事件，**Then** 结果被正常解读（等价于同一段文本），回合继续，不再判为流损坏。
3. **Given** 一次经 MCP 工具成功回流的真实回合（子代理委派或外部工具），**When** 该回合结束，**Then** 结果与 usage 回收进主会话，进程以正常退出码收口，镜像可审计该工具结果事件。
4. **Given** 引擎版本与 pin 一致，**When** 用户启动会话，**Then** 不产生漂移告警；**Given** 版本不一致，**When** 未显式放行，**Then** 仍按治理语义拒绝启动（放行时留痕）——治理红线不因本次修复而放宽。

### User Story 2 - 上游升级时能立刻发现形状漂移 (Priority: P2)

下一次上游发布把工具结果形状再改一次，或者把某个字段改回字符串。维护者在升级流程中先用真实事件样本重录 fixture、跑全量门禁：解码器对新形状的容忍/拒绝行为立刻可见，不用等到真实委派冒烟断流才发现。

**Why this priority**: 本次缺陷的根因不只是「解码器只认一种形状」，还有「没有新形状的样本可供回归」。样本入库后，同类漂移在门禁层面暴露，成本从「一次真实冒烟」降到「一次测试」。

**Independent Test**: 仓库内提交覆盖新旧两种工具结果形状的真实样本，全量门禁逐行解码无错；人为把样本改回未知形状时门禁失败。

**Acceptance Scenarios**:

1. **Given** 仓库提交了 2.1.296 的真实事件样本，**When** 跑全量门禁，**Then** 样本逐行解码无错且关键字段（工具调用 id、内容文本、错误标记）被断言。
2. **Given** 样本被改成解码器未建模的第三种形状，**When** 跑门禁，**Then** 测试失败（容忍有边界，不是「什么都放过」）。

### Edge Cases

- 工具结果内容为**空数组**或**元素全为空文本块**时怎么办？——解读为空文本，不视为流损坏（与「字符串为空」同等对待）。
- 工具结果内容数组里混有非文本块（如未来新增的图片/结构化块）时怎么办？——判为流损坏（见 FR-103 与 Clarifications Q1：容忍的是已建模的两种形状，未建模的块类型不得被静默消化或伪装成文本；未来出现新块类型时走升级流程显式建模）。
- 工具结果内容为 `null` 或字段缺失时怎么办？——解读为空文本（旧行为下字段缺失即空串），不视为流损坏。
- 内容数组里嵌套了非法结构（如对象而非文本块）时怎么办？——按既有 fail-closed 红线判为流损坏（不静默丢弃）：容忍的是**已建模的两种形状**，不是任意畸形数据。
- 工具结果事件同时存在结构化摘要字段（`tool_use_result`）时怎么办？——与内容形状无关，原样保留（沿用既有语义）。
- 引擎版本比 pin 更新但形状未变时怎么办？——仅在版本号上告警/拒绝（治理语义），与形状容忍相互独立。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-101**: mulix 的流解码器 MUST 同时接受工具结果内容的两种形状：**单字符串**（2.1.291 及之前）与**文本块数组**（2.1.296 及以后），两种形状解读为同一段文本；任一形状都不得被判为流损坏。
- **FR-102**: 数组形状的解读 MUST 保留工具调用标识与错误标记（`tool_use_id`、`is_error` 条件字段语义不变：成功缺省为假）；结构化摘要字段（`tool_use_result`）的保留语义不变。
- **FR-103**: 形状容忍 MUST 有边界：空数组、空文本块、`null`/缺失内容 → 空文本（不放行也不断流）；数组中出现解码器未建模的非文本结构（含图片块、未来新增的结构化块）、非块畸形元素 → 一律按流损坏 fail-closed（与「非法 JSON」同类），不得静默丢字段或伪装内容——数组元素只认 `{type:"text"}` 文本块。
- **FR-104**: 仓库的引擎版本 pin MUST 更新为目标版本（本机实测的新版本），pin 值 MUST 与该版本 `claude --version` 的精确输出一致；pin 更新 MUST 同时记录时间。
- **FR-105**: 仓库 MUST 提交覆盖**新形状**的真实引擎事件样本（fixture），供门禁回归；取材时序：优先从 P2 冒烟的引擎 transcript 中提取可直接入库的完整事件，字段不完整的关键场景（如错误标记）在 2.1.296 真实冒烟时补采；样本 MUST 取自真实 CLI 输出（不得手工编造），且与既有样本一样满足「无空行、逐行可解码」的入库约定。
- **FR-106**: 门禁 MUST 对两种形状都有断言：旧形状样本继续通过（无回归），新形状样本通过且关键字段被断言；第三种未知形状必须导致失败。
- **FR-107**: 一次**真实引擎**冒烟 MUST 复现并关闭 P2 的限制条目：真实委派链（子代理创建→真实多步工作→结果与 usage 回收）跑完，且至少一次真实外部工具回合的结果回流被正确解读；冒烟 MUST 记录引擎版本、退出码与关键输出摘录。
- **FR-108**: 若真实冒烟因环境原因（凭据、网络、安装约束）无法完成，MUST 如实记录未完成的原因与已完成部分，并把它路由到后续处理——不得以自动化测试结果冒充真实冒烟。
- **FR-109**: 引擎版本治理语义 MUST 保持不变：pin 一致时不告警；不一致时默认拒绝启动并提示放行开关；显式放行时留痕（漂移事件入镜像）。本次修复不得引入「静默接受任意版本」。
- **FR-110**: 引擎版本 pin 中预留的缓存基准位 MUST 在本阶段回填：以真实冒烟会话（FR-107）的缓存记账实测值回填 `baseline.cache_hit_rate`，并在备注中写明测量条件（单次真实会话、日期、任务类型）；冒烟因 FR-108 未能完成时，基准位 MUST 改为明确标注「尚未建立」及原因——不得继续保留 P1 的占位文案而对外声称已治理。
- **FR-111**: 本次变更 MUST NOT 放宽 P1/P2 的事件红线（未知顶层类型跳过、非法 JSON fail-closed、先持久化后发布、镜像 1:1）。

### Key Entities *(include if feature involves data)*

- **引擎版本 pin（Engine Lock）**: 仓库根治理文件；记录目标 CLI 版本、版本字段探针、pin 时间与缓存基准。升级流程 = 改 pin + 重录样本 + 基准对比。
- **工具结果事件（Tool Result Event）**: `user` 类事件，承载一次工具调用的回流；关键属性为工具调用标识、内容（两种形状）、错误标记、结构化摘要。
- **事件样本（Fixture）**: 真实引擎一轮或多轮输出逐行留存的文件；入库约定为无空行、逐行可解码；是形状漂移的第一道回归线。
- **冒烟证据（Smoke Evidence）**: 真实引擎跑真实任务的记录（版本、工作区、关键输出、退出码、提交产物）；与自动化门禁分开归档。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 pin 所指的真实引擎版本上，一次真实子代理委派完成多步编码任务（读改测提交），结果与 usage 回收进主会话，进程正常退出；全程事件可审计——关闭 P2 `report.md` 的「诚实限制」第 1 条。
- **SC-002**: 新旧两种工具结果形状在同一套门禁下都通过，未知的第三种形状失败（容忍有边界，可回归）。
- **SC-003**: 仓库不再出现「本机 CLI 必须降级到旧版本才能跑通委派」的缓解要求；pin 值与本机实测版本一致，`doctor` 无漂移告警。
- **SC-004**: 版本漂移治理行为与 P1/P2 一致（不一致即拒绝启动或留痕放行），升级流程可复用（改 pin → 重录样本 → 门禁 → 基准）。
- **SC-005**: 缓存基准位不再是指明「P3 后回填」的占位文案：优先以冒烟会话的缓存记账实测值回填（注明测量条件）；冒烟未跑成时明确标注为尚未建立（诚实记录优先于形式合规）。

## Assumptions

- 上游工具结果内容形状在 2.1.296 由字符串改为文本块数组；这已被 P2 冒烟的真实断流与引擎 transcript 证实，本次以其为建模依据。
- 执行时序（Clarifications Q2）：当前本机 CLI 因临时缓解停在 2.1.291；执行阶段第一步是重新升级到 2.1.296，随后改 pin、在 2.1.296 上跑真实冒烟并顺路采集新形状样本。升级失败属于 FR-108 的环境约束情形。
- 本机 claude CLI 与仓库 pin 之间存在版本差是常态（上游发布快于治理节奏）；本次以「把 pin 推到现实、并让解码器容忍一次形状迁移」为解法，长期仍要求升级时重录样本。
- 真实冒烟需要本机 claude 凭据与网络可用；不可用时按 FR-108 如实记录并路由。
- 缓存命中基准依赖既有缓存度量口径（P1 已交付的用量/缓存记账），不新增度量面。
- 其余 P3 路由项（单飞清理、大行隔离、watcher 复测、计数修正、解析边缘、allowlist 漂移、fsync、启动后新建文件监控等）不在本变更集内，另行排期。

## Out of Scope

- T11-① 单飞 leader panic 悬挂与裁决表无界增长（defer 式清理）。
- T5-① 超过 16MB 的行导致的硬失败（隔离为损坏段）。
- T12-⑤ watcher 真实会话复测与 `p2-smoke.md` 限制 #3 修正、T12-⑥ SC-006 计数修正。
- T10-① 解析器注释边缘、T10-② allowlist 漂移交叉断言、T5-⑤ fsync、T8-① 等 `iw.Done`、T8-② 启动后新建文件监控（FR-109 后半产品裁定）及廉价测试补强清单。
- 任何新功能（子代理调度、记忆、外部 server、钩子的能力扩张）。
- 多版本 CLI 并存/自动安装/自动升级工具链。
