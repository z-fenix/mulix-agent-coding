# Feature Specification: Claude CLI 托管路线的 dsh 功能等价

**Change**: `2026-10-15-claude-cli-hosted-dsh-parity`

**Created**: 2026-10-15

**Status**: Approved specification — 用户于 2026-10-15 明确批准当前总纲规格；仅覆盖总纲，不代替各独立 change 的设计、任务或归档审批

**Input**: User description: "保持托管 Claude CLI，并在外围负责镜像与治理，进行dsh 的功能等价复刻"；后续裁定："保留完整等价目标，将它作为总纲，拆成多个独立 change 逐项交付"

本规格作为完整功能等价的总纲，不将整张清单压入一次产品实现。各能力通过独立 change 交付，分别明确范围、依赖、验收证据及未闭合缺口；以下场景和成功标准用于总目标汇总，不自动成为任一子 change 的全量实现范围。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在既定托管路线下获得可信的等价承诺 (Priority: P1)

作为使用者，我希望继续由 Claude CLI 驱动编码任务，同时准确知道每项功能由谁提供、是否真正可用，以及与 dsh 有何可观察差异，避免把已有机制、开发工作流资产或同名功能误当成产品等价。

**Why this priority**: 用户已选择保留托管路线；所有后续能力都必须以这条约束为前提，不能通过偷偷替换主引擎或降低验收语义完成目标。

**Independent Test**: 核对完整能力清单，并运行一个既有编码会话；用户能够区分宿主能力、引擎委托能力和未完成能力，原有镜像与治理行为不退化。

**Acceptance Scenarios**:

1. **Given** 使用默认配置，**When** 发起含工具调用的编码任务，**Then** Claude CLI 仍执行推理和模型—工具迭代，mulix 继续管理宿主镜像和治理，不要求改用自管模型循环。
2. **Given** 一项能力依赖引擎，**When** 查询其状态，**Then** 可见受测引擎版本、依赖条件、验证证据和限制，不标为 Go 宿主独立实现。
3. **Given** 仅有镜像分支、固定 profile 或只读工具执行等部分能力，**When** 对照完整验收场景，**Then** 不得分别宣称上下文 fork、动态插件组合或完整 PTC 已等价。

---

### User Story 2 - 连续对话、历史分支与长任务不会失去有效上下文 (Priority: P1)

作为长任务使用者，我希望会话恢复、指定切点分支、压缩和子代理继承的历史实际参与后续推理，而不只是出现在审计记录中。

**Why this priority**: 这是镜像审计与可继续工作上下文的核心区别，也决定恢复与委派是否可信。

**Independent Test**: 在历史中放入可检查的约束，恢复或分支后完成依赖该约束的任务；验证选定切点后的信息不会混入新分支，源会话不被修改。

**Acceptance Scenarios**:

1. **Given** 已结束的多轮会话，**When** 重新打开并继续工作，**Then** 先前有效对话能够实际影响后续请求，并能追溯恢复来源。
2. **Given** 历史中先后出现事实 A 和事实 B，且选择 A 之后、B 之前的有效切点，**When** 创建上下文分支并继续任务，**Then** 新分支继承切点前的有效对话、不继承 B，且不会重执行历史工具副作用。
3. **Given** 超出可用上下文容量的长任务，**When** 自动压缩或发生容量溢出，**Then** 明确显示处理结果，保留关键约束和可追溯来源；无法安全恢复时明确失败，不静默开启空白会话。
4. **Given** 需要子代理接续的任务，**When** 分别使用 fresh spawn 与上下文 fork，**Then** 两种模式的继承范围明确、实际生效，子代理支持后续消息、状态观察和取消。

---

### User Story 3 - 按配置组合扩展、技能和工具 (Priority: P1)

作为扩展使用者，我希望安装、启停、组合插件和技能，为不同 agent 配置不同工具集合，并在明确的生效边界内更新，而不必为每种组合重新修改产品源码。

**Why this priority**: kernel 接缝只有成为可配置、可验证的用户能力，才达到动态插件系统的功能目标。

**Independent Test**: 在测试工作区中安装测试扩展，切换 profile/preset，调用技能及两种传输的外部工具；比较多个 agent 的可见工具集合，并验证失败变更不会留下部分生效状态。

**Acceptance Scenarios**:

1. **Given** 一组有依赖的插件，**When** 安装、启停或更新配置，**Then** 依赖错误会阻止变更并给出诊断，合法组合能实际影响后续任务，失败时不残留注册效果。
2. **Given** 不同的 launcher profile 和 agent preset，**When** 启动或创建 agent，**Then** 实际扩展与工具组合符合配置，而不只是改变显示名称。
3. **Given** 已发现的产品技能，**When** 用户通过 `/skill-name` 或模型按需调用，**Then** 对应内容被正确加载到目标 agent 的有效上下文；仓库开发流程技能不被自动算作产品能力。
4. **Given** 分别提供 stdio 和 Streamable HTTP 的外部 MCP 工具，**When** 配置到指定 agent，**Then** 目标 agent 可调用、其他 agent 不越权获得该工具，拒绝和失败可审计。
5. **Given** 回合中发生扩展变更，**When** 更新、卸载或热重载，**Then** 不撕裂当前已冻结工具面，明确告知下一回合生效或必须重启，未受影响的组合保持可用。

---

### User Story 4 - 扩展执行受统一治理与实际隔离约束 (Priority: P1)

作为工作区所有者，我希望普通工具调用、程序式工具调用、外部工具和扩展拦截遵循一致的授权边界；声称被隔离的执行必须真正不能越过文件系统和网络限制。

**Why this priority**: 扩大工具与插件覆盖面不得绕过现有治理；审批与 OS 执行隔离必须分别证明。

**Independent Test**: 对普通工具与 PTC 执行同一组允许/拒绝用例；用无破坏性探针验证越界读写及受限网络访问被阻止，检查拒绝前后审计顺序。

**Acceptance Scenarios**:

1. **Given** agent 能见且被授权的工具，**When** 通过程序式调用执行，**Then** 与直接调用使用一致的权限裁决和审计，不局限于与 agent 实际工具面无关的本地只读子集。
2. **Given** 拦截扩展需要拒绝、修改输入或替换结果，**When** 在受支持的生命周期接缝执行，**Then** 行为真正生效且可审计，不允许抬高权限或覆盖治理拒绝。
3. **Given** 配置的执行隔离边界，**When** 工具尝试越界文件访问或被禁网络访问，**Then** 执行层实际阻止该效果，而不仅仅展示审批提示。
4. **Given** 平台仅支持部分隔离或引擎缺少必要接缝，**When** 请求更强保证，**Then** 明确拒绝该保证，不静默无沙箱运行，也不宣称与更强平台等价。

---

### User Story 5 - 使用远程入口、搜索和回放管理同一类任务 (Priority: P2)

作为本地或远程使用者，我希望通过终端、浏览器和程序入口操作会话，恢复连接后继续观察任务，并搜索和查看历史，而不需要接触内部审批桥或引擎私有文件。

**Why this priority**: 这是产品入口等价，不代替上下文、工具和治理能力本身。

**Independent Test**: 通过受支持入口启动、继续、中断同一个受控任务；断线后恢复观察；查询测试会话历史并回放，确认回放不会再次执行工具。

**Acceptance Scenarios**:

1. **Given** 已获授权的远程客户端，**When** 创建、继续、观察或中断会话，**Then** 操作与本地执行遵守同一治理语义，断线重连不重复提交任务。
2. **Given** 无授权客户端或越权会话标识，**When** 尝试读取、控制或订阅，**Then** 被拒绝且不泄露会话内容或凭据。
3. **Given** 已持久化的会话集合，**When** 搜索并选择历史记录，**Then** 能定位到对应会话及事件；回放保留顺序和分支来源，不产生历史执行副作用。

---

### User Story 6 - 在明确支持的模型供应商上完成任务 (Priority: P2)

作为多模型使用者，我希望明确区分模型名切换与真实供应商接入，并在受支持的供应商上完成含工具调用的任务。

**Why this priority**: 用户的差异清单包含多 Provider；保留主引擎不能成为把这一差异悄悄删除的理由，但能否在该约束下完整覆盖仍需确认边界。

**Independent Test**: 针对批准的每个供应商，用真实请求完成流式输出、工具调用和多轮继续；仅修改模型名、伪造事件或配置一个未运行的路由不得通过。

**Acceptance Scenarios**:

1. **Given** 一个声明支持的供应商，**When** 执行真实多轮工具任务，**Then** 可验证请求确实到达该供应商，响应和用量可解释，错误不会被伪装为成功。
2. **Given** 当前托管引擎不支持所请求的供应商或功能，**When** 尝试启动，**Then** 明确报告不支持及约束；不能静默换用另一个供应商，不能因此宣称全量功能等价。

### Edge Cases

- 引擎升级、降级或替换后，曾验证的委托功能可能消失；能力状态必须与受测版本绑定。
- 镜像存在但引擎原生会话丢失、过期或无法读取时，不得把镜像可读误报为上下文已恢复。
- 分支切点落在未完成工具交互、损坏段或压缩边界时，不得生成表面成功但历史不自洽的分支。
- 插件依赖缺失、循环依赖、名称冲突、卸载失败或回合中更新时，禁止半生效状态及旧权限残留。
- 技能或外部工具包含恶意指令时，不能由此获得宿主配置权、审批权或访问其他 agent 的私有上下文。
- 权限请求无人响应、形态未知、输入非法或执行流损坏时，继续遵守 fail-closed，不用默认允许保活。
- 取消、进程崩溃或客户端重连与工具完成并发时，不能重复执行副作用、重复发布终态或绕过先持久化后发布。
- Windows、Linux、macOS 隔离能力不一致时，分别标注、分别验收，不把部分隔离统称完整沙箱。
- 独立 agent、session、进程或上下文 fork 不等于文件系统工作区隔离；没有单独配置工作区时不得宣称已隔离。
- 模型回答具有随机性；等价验收比较可观察的功能契约，不要求逐字相同的模型输出。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 保留“Claude CLI 作为主驱动，mulix 在外围负责镜像与治理”的产品路线；本规格不授权以自管模型循环替换主路线。
- **FR-002**: 系统 MUST 对用户提供的全部 16 个差异方向建立能力记录：模型—工具循环、多供应商、插件安装与热组合、profiles/presets、工具与 MCP、技能运行时、自动压缩、会话上下文权威、会话 fork、子代理、PTC、hook/middleware、OS 沙箱、交互及远程入口、搜索、replay。原表的“搜索 / Replay”拆为两个方向，避免遗漏不同验收语义。
- **FR-003**: 每项能力 MUST 分别记录提供方（宿主/委托引擎/共同）、验收状态（未验证/部分通过/通过/受约束不支持）、版本、前提、限制及证据；提供方不等于验收状态。
- **FR-004**: 等价判定 MUST 基于固定 dsh 参考版本的可观察契约，不以同名、存在接口、开发资产、自动化模拟或里程碑完成为依据。本轮参考源码位于 `C:\Users\Administrator\workplace\project\tools\deepseek-harness`，固定提交为 `571902028a75c64c1d767f4ae5fd099485f0ddf0`，根包声明版本为 `0.2.1-alpha.3`。后续仓库 HEAD 移动不得自动改变本轮基线；用户比较表仍是待逐项核验的输入，不冒充已完成全部源码核验。
- **FR-005**: 引擎委托能力 MUST 经过 mulix 产品入口的端到端验证后才能计为产品已具备；仅证明独立 Claude CLI 具备该能力不足以通过。
- **FR-006**: 不可在托管约束下达成的参考契约 MUST 显式列为未闭合缺口。未获用户裁定前，MUST NOT 擅自删减目标或改写为降级验收；存在缺口时不得宣称全量功能等价。
- **FR-007**: 系统 MUST 保持镜像先持久化后发布、镜像单写者及现有 1:1 审计不变量；新增功能不能将审计顺序或权限拒绝语义退化。
- **FR-008**: 系统 MUST 分别说明宿主审计真源与引擎有效上下文的权威边界；恢复、分支、压缩及子代理继承 MUST 证明历史实际送达推理上下文，而不只是复制审计记录。
- **FR-009**: 会话恢复 MUST 保留有效历史与来源；无可用恢复材料时 MUST 明确失败，不静默空会话续接。
- **FR-010**: 上下文 fork MUST 继承选定有效切点前的完整有效对话、排除之后内容、保持源会话不变，并且不重执行历史工具。仅复制镜像、lineage 或提供摘要种子 MUST NOT 算作无损上下文 fork；有损继承须独立命名和披露。
- **FR-011**: 长任务 MUST 具备可验证的自动压缩及溢出处理，保留关键任务约束和可追溯来源，并区分引擎执行与宿主执行。
- **FR-012**: 子代理 MUST 支持 fresh spawn、上下文 fork、后续消息、状态观察、取消、并发约束和明确的工作区共享边界。
- **FR-013**: 用户 MUST 能够安装、启停、组合及更新扩展，并获得依赖错误诊断和失败恢复；无需为每个合法组合修改产品源码。
- **FR-014**: 用户 MUST 能够分别配置启动 profile 和 agent preset，使配置决定实际能力组合；固定 standard/minimal 的工具开关不足以单独满足该要求。
- **FR-015**: 动态扩展变更 MUST 有明确生效边界；回合中冻结的工具面保持一致。可以延后生效或要求重启的具体条件须对用户可见，不能把所有变更都宣称支持热更新。
- **FR-016**: 工具可见性与调用权限 MUST 按 agent 隔离；本地、外部 MCP 与程序式调用 MUST 遵守相同治理拒绝，不因调用入口变化获得额外授权。
- **FR-017**: 产品 MUST 支持使用 stdio 及 Streamable HTTP 的外部 MCP 工具，并正确处理断连、取消、拒绝和工具集合变化。
- **FR-018**: 产品 MUST 支持技能发现、解析、按需加载、用户 `/skill-name` 调用及模型调用；技能内容须进入指定 agent 的有效上下文，开发工作流文件的存在不构成验收。
- **FR-019**: PTC MUST 能调用目标 agent 可见且获授权、声明为该入口可用的工具，并经过统一治理；对工具覆盖、资源边界、取消和执行隔离的限制必须明确，不能将“只读”误报为“已隔离”。参考基线中更广工具覆盖的差异须逐项关闭或保持未通过。
- **FR-020**: hook/middleware MUST 按参考契约支持实际执行控制，包括适用接缝上的拒绝、输入修改、结果修改和执行包围；观察式 hook 不计为同等拦截。任何扩展 MUST NOT 覆盖治理拒绝；修改后的实际执行目标及输入必须重新满足授权条件，不能沿用修改前的允许决定。原始结果与扩展后的用户可见结果必须可区分追溯。
- **FR-021**: 声明启用执行沙箱时 MUST 实际约束所声明的文件和网络效果；审批、路径提示、独立进程和语言运行时隔离不得替代 OS 效果约束。
- **FR-022**: OS 隔离 MUST 按平台公布受支持边界与不支持条件；达不到所请求保证时拒绝启动该受限任务，不静默降级为无隔离执行。
- **FR-023**: 产品 MUST 提供经授权的浏览器与程序化远程会话操作，覆盖创建、继续、观察、中断、重连；不得把内部审批桥或只读观察面当成公共会话入口。
- **FR-024**: 远程操作 MUST 默认不公开，授权检查同时覆盖会话控制与事件读取；断线重连不能重复提交任务或泄漏凭据。
- **FR-025**: 用户 MUST 能够搜索持久会话集合并定位对应会话和事件，检索边界、默认启用状态与参考基线的差异必须可见。
- **FR-026**: 用户 MUST 能够通过产品入口查看历史回放，保留原顺序及分支来源；审计回放不得重执行历史工具，测试用模型 replay 必须独立标识。
- **FR-027**: 多供应商支持 MUST 以真实供应商请求、流式输出、工具调用、多轮继续及可解释用量验收，不以模型名、路径切换或配置存在代替。参考基线中的非 Claude 模型协议继续保留在完整目标内；托管引擎不支持的部分保持未闭合缺口，不因分批交付而自动豁免。任何涉及改变主驱动路线或缩减目标的取舍，须凭具体证据另行提交用户裁定。
- **FR-028**: 现有缓存治理、费用估算、长期记忆、TUI 和可选观察能力 MUST 保留其现有契约；费用展示继续明确估算属性，不能宣称为供应商精确账单。
- **FR-029**: 每项新增或委托能力 MUST 同时验证正常路径、权限拒绝、取消和可适用的故障恢复；真实集成验证受环境阻塞时须记录阻塞，不得用模拟测试替代真实通过。
- **FR-030**: 交付 MUST 保留完整等价目标，以本规格为总纲，拆成多个独立 change 逐项实现和验收，不要求本次单个 change 一次完成全部产品功能。分批完成只证明相应条目通过，不代表其余条目自动完成。
- **FR-031**: 每个独立 change MUST 关联所覆盖的总纲需求、明确其依赖与验收范围，并分别遵守规格、设计、任务和归档的显式审批。能力记录 MUST 关联负责交付的 change 与证据，能区分已交付、部分交付、未交付及阻塞项；拆分本身不构成实现授权。

### Key Entities *(include if feature involves data)*
