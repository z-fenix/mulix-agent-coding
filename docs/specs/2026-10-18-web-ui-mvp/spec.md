## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在浏览器中运行并观察一个会话回合 (Priority: P1)

用户在本机启动 mulix 的 Web 界面，选择工作区，新建一个会话并提交一条任务。他们在浏览器里实时看到：助手输出的流式渲染（markdown、代码高亮）、每次工具调用的卡片（工具名、输入摘要、结果、耗时）以及文件编辑的 diff 视图，直到回合收口。全程不需要打开终端。

**Why this priority**: 这是「比 TUI 更好看的交互界面」的核心价值所在；没有实时观察，其余故事都不成立。

**Independent Test**: 启动服务 → 浏览器打开 → 提交一条会触发工具调用与文件编辑的任务 → 观察流式输出、工具卡片与 diff，直到回合完成。

**Acceptance Scenarios**:

1. **Given** 服务已启动且已选择工作区，**When** 用户提交一条 prompt，**Then** 输入被受理，界面出现回合进行中的状态，助手输出随引擎产生逐段流式呈现。
2. **Given** 回合进行中且助手调用了一个工具，**When** 工具开始执行并返回结果，**Then** 界面出现一张工具卡片，含工具名、输入摘要、结果与耗时；若工具是文件编辑，则以 diff 形式渲染变更。
3. **Given** 一个已存在的历史会话（镜像中有完整事件记录），**When** 用户在界面中打开它，**Then** 完整 transcript 从镜像回放呈现，且损坏段（半行/超限行）以明确标记展示，不吞内容。

---

### User Story 2 - 在浏览器中审批工具调用 (Priority: P1)

当某次工具调用按当前权限策略需要审批时，浏览器界面弹出审批请求，用户可以批准或拒绝；审批决定与其痕迹照常进入镜像审计面。当没有任何界面在线应答时，请求按既有 fail-closed 语义被拒绝，绝不静默放行。

**Why this priority**: 审批是治理三层的核心交互，fail-closed 是项目红线；Web 端不还原它就不能替代 TUI。

**Independent Test**: 以需要审批的权限配置提交一条会触发受治理工具的任务 → 界面出现审批请求 → 批准后工具继续执行；另以断开所有界面的方式复测 → 请求被拒绝且有审计痕迹。

**Acceptance Scenarios**:

1. **Given** 权限策略要求某工具调用先审批，**When** 引擎发起该调用，**Then** 界面在同一回合内弹出审批请求，展示工具名与调用摘要。
2. **Given** 审批请求展示中，**When** 用户选择批准，**Then** 工具继续执行，回合继续；**When** 用户选择拒绝，**Then** 引擎收到拒绝结果，回合按拒绝路径继续。
3. **Given** 审批请求发起时没有任何浏览器客户端在线，**When** 请求无人处理，**Then** 该调用立即被拒绝收口；交互端在线但无人应答时，等待至既有 120s 治理窗口到期后被拒绝——两者均不静默放行，且决定过程在镜像中留痕。
4. **Given** 一次已完成的审批，**When** 用户回看 transcript，**Then** 能看到该次审批的发生与结果。

---

### User Story 3 - 会话管理与断线恢复 (Priority: P2)

用户可以列出历史会话、新建会话、在多个会话间切换；切换或浏览器刷新/断线重连后，界面从镜像追平到最新状态，不丢事件、不重复渲染。回合进行中关闭浏览器不影响回合继续执行。

**Why this priority**: 没有它，Web 界面只能一次性使用；但它是围绕核心观察/审批体验的周边能力。

**Independent Test**: 创建两个会话并各自运行回合 → 刷新浏览器与切换会话 → 验证回放完整且与镜像 1:1；回合中关闭浏览器再重开 → 回合结果完整可见。

**Acceptance Scenarios**:

1. **Given** 已有多个会话，**When** 用户打开会话列表，**Then** 看到各会话的标识、状态（进行中/空闲）与最近活动时间，并可选择进入或新建。
2. **Given** 回合进行中用户关闭了浏览器标签页，**When** 回合继续执行并收口，**Then** 事件照常先写镜像；用户重新打开界面后能看到完整过程与结果。
3. **Given** 浏览器与服务的连接中断后恢复，**When** 界面重连，**Then** 从镜像追平缺失的事件，呈现与未断线时一致的最终状态。

---

### User Story 4 - 引擎与守卫状态可见 (Priority: P3)

当引擎因 engine.lock 漂移被拒绝启动时，或镜像出现损坏段被隔离时，界面如实呈现原因与痕迹，而不是让用户面对无声失败。

**Why this priority**: 属于 fail-closed 在 UI 侧的呈现义务，不是新能力，但缺少它会破坏信任。

**Independent Test**: 构造引擎版本漂移后启动 Web 界面 → 界面显示明确的拒绝原因；构造含损坏段的镜像 → 界面标记损坏段。

**Acceptance Scenarios**:

1. **Given** 引擎版本与 engine.lock 不符，**When** 用户尝试启动会话，**Then** 界面展示拒绝启动的原因与放行留痕入口，而非静默失败或无限等待。

---

### Edge Cases

- 引擎子进程在回合中途崩溃：界面呈现回合异常收口的状态与错误信息，镜像保留已发生事件。
- 镜像文件含损坏段（半行/超限行）：好行照读、损坏段隔离转储并在界面标记，不整体硬失败。
- 同一服务被多个浏览器标签页同时打开：后打开者只读跟随，仅先建立的连接持有提交/审批交互权，不产生重复审批决定。
- 超长 transcript（数千事件）：回放与追平不因此卡死或丢失尾部事件。
- prompt 提交在回合未收口时被拒：界面如实提示「回合未结束」，与现有放行下一次 Submit 的语义一致。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 提供一个由 mulix 启动的本地服务入口，用户在浏览器中打开其地址即可使用本变更的全部界面功能；默认仅监听本机回环地址，端口有默认值且可配置。
- **FR-002**: System MUST 在界面中提供会话列表、新建会话、进入既有会话；列表展示标识、状态与最近活动时间。
- **FR-003**: System MUST 在打开会话时从持久镜像回放完整 transcript，并遵循损坏段隔离语义（好行照读、损坏段明确标记、不吞内容、不整体硬失败）。
- **FR-004**: System MUST 将回合中的助手输出逐段流式呈现于界面，支持 markdown 与代码高亮渲染。
- **FR-005**: System MUST 为每次工具调用呈现工具卡片（工具名、输入摘要、结果、耗时），文件编辑类调用 MUST 以 diff 形式渲染变更。
- **FR-006**: Users MUST be able to 提交 prompt 发起回合；回合未收口时的新提交 MUST 被拒绝并明确提示，与现有回合收口后放行下一次提交的语义一致。
- **FR-007**: Users MUST be able to 中断一个进行中的回合，界面呈现中断后的收口状态。
- **FR-008**: System MUST 将需要审批的工具调用以可交互的审批请求呈现在界面，用户可批准或拒绝；决定沿既有审批桥生效。
- **FR-009**: System MUST 将需要审批的工具调用以可交互的审批请求呈现在界面，用户可批准或拒绝；决定沿既有审批桥生效。审批等待受既有 120s 治理窗口约束：交互端在线期间持续等待至窗口到期，窗口到期按既有 timeout 语义 fail-closed 拒绝（与 TUI 行为一致）；交互端全部断开时立即拒绝；两者均绝不静默放行，决定过程 MUST 在镜像中留痕。
- **FR-010**: System MUST 在事件于界面可见之前先将其写入镜像（先持久化后发布），镜像与界面所见保持 1:1。
- **FR-011**: Users MUST be able to 在界面中选择工作区目录；未选择工作区时提交入口 MUST 不可用。
- **FR-012**: System MUST 支持浏览器断线重连与页面刷新后从镜像追平事件，最终呈现与未断线一致，不丢事件、不重复渲染。
- **FR-013**: System MUST 在界面如实呈现引擎启动被拒（如 engine.lock 漂移）等原因，不得静默失败。
- **FR-014**: System MUST 保证回合同期在浏览器关闭后继续执行并照常收口（界面关闭不终止回合）。
- **FR-015**: System MUST 在打开会话时检查跨进程会话锁（pid+心跳工件）：锁新鲜则 fail-closed 拒绝并呈现持有者 pid，过期/缺失可接管。
- **FR-016**: System MUST 对全部变更类端点实施同源防护（SameSite=Strict Cookie + Origin 校验），缺失或异源一律拒绝。

### Key Entities *(include if feature involves data)*

- **会话（Session）**: 一次可持续交互的容器；有标识、状态（进行中/空闲/异常）、工作区归属；其全部事实以事件形式持久于镜像。
- **回合（Turn）**: 会话内一次提交到收口的生命周期；有状态（进行中/已收口/中断/异常）。
- **事件（Event）**: 镜像中的最小事实单元（助手输出、工具调用、审批请求与决定等）；先镜像后界面，1:1。
- **审批请求（Approval Request）**: 一次待治理决定的工具调用；含工具名与调用摘要、决定（批准/拒绝/无人应答拒绝）、留痕。
- **工作区（Workspace）**: 会话运行所针对的项目目录；选择后方可提交。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户从打开界面到提交第一条 prompt 并看到流式输出，全程不使用终端，可在 1 分钟内完成。
- **SC-002**: 引擎产生的事件在已连接界面上可见的延迟不超过 1 秒。
- **SC-003**: 断线重连或刷新后，界面呈现的事件序列与镜像完全一致（无缺失、无重复），可通过对照镜像验证。
- **SC-004**: 审批请求在有人应答时由用户决定、在无人应答时一律拒绝，拒绝率达 100%（无人应答场景），并有对应审计痕迹。
- **SC-005**: 打开一个含数千事件的历史会话，回放在 5 秒内完成且尾部事件完整。

## Assumptions

- 单用户本机使用场景：服务默认仅监听回环地址，MVP 不做认证与公网部署（公网/反代属路线图第五期）。
- 同一时刻一个交互端：同一会话被多个标签页打开时，后打开者为只读跟随，只有先建立的连接持有提交/审批交互权（2026-10-18 clarify 裁定）。
- 界面文案默认中文，术语与现有 TUI/镜像保持一致。
- 既有 TUI 不受影响，本变更为并行的呈现通道；治理、镜像、回合收口等语义完全复用现有实现，不改变其行为。
- 前端与桌面的技术栈选型（框架、构建工具、桌面壳）留给设计期裁定，不在本 spec 固化。设计期裁定与批准记录（2026-10-18）：npm 工具链与 12 包依赖清单已批准，前端进本期；会话列表状态为启发式推导（服务外进程死于回合中途的会话显示「进行中」直到被打开——已知边界）。

## Out of Scope

- 桌面版壳（路线图第四期）
- 权限矩阵编辑、Provider/引擎设置页、Usage/缓存记账展示、会话搜索与 fork、子代理视图（第二期）
- 计划/待办面板、文件树、定时任务、钩子事件流、插件管理 UI（第三期）
- 插件市场、GitHub review、MCP memory、网络代理、公开部署（第五期）
