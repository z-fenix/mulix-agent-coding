## 3. 三类责任分别证明

**有效推理上下文由托管引擎实际提供。** 恢复、fork、自动压缩和子代理继承需要证明有效历史参与后续工作。复制审计前缀、lineage 或提供摘要，不等于无损上下文 fork。优先接通受支持的引擎原生能力，但不能预设一个参数就能满足任意历史切点。

**审计与治理仍由宿主负责。** 所有新路径保留先持久化后发布、镜像单写者、1:1 和 fail-closed。PTC、外部 MCP、扩展拦截和远程控制不得因入口变化获得额外权限；拦截修改后的实际目标与输入必须满足重新授权条件。

**产品入口必须接通真实受治理会话。** 内部审批桥不是公共会话 API，NATS 只读观察面不是控制入口，开发工作流技能不是产品技能运行时。CLI、TUI、MCP、公共服务、Web 与程序客户端的能力声明分别验证。

独立 session、进程或上下文分支不自动隔离工作区。没有单独配置时不能宣称独立 worktree 或文件系统隔离；审批、只读工具标记和语言运行时也不等于 OS 沙箱。

## 6. 推进顺序与不可绕过的门槛

建议先交付 B0，再以 B1 为首条功能主线；同时尽早检查 B12 与 B11 的可行性，不先建 Web 外壳再发现核心能力无法支持。

- B0 完成参考清单和状态记录，不表示清单上的功能已经通过；本次初始 JSON 也不等于 B0 产品查询服务已实现。
- B1 必须区分“CLI 有参数”“mulix 已接通”“产品旅程真实通过”。不能把 `--fork-session` 参数存在视为完整上下文 fork 已完成。
- B4 若无法安全实时更新引擎工具面，明确选择后续会话或受控重启边界。只有安全续接已验证，才能用重启承载变更；不能静默丢弃上下文。
- B12 先核对受支持的供应商接入是否维持主驱动语义。模型名、可执行路径或静态配置存在都不是多供应商验收；不得暗中加入另一主引擎或自管模型 loop。
- B9 对每个生命周期接缝分别验证。能拦截某类工具不表示能任意改写模型请求；观察 hook 不替代有决策效果的拦截链。
- B10 的只读工具也必须经过统一治理；JavaScript 中断、Go handler 的实际取消、进程效果约束分别验证。
- B11 对每个平台运行授权范围内的无破坏性越界探针。未测平台保持未验证；部分隔离不得宣称完整沙箱。

主驱动约束与参考功能不能同时满足时，暂停受影响交付项并带具体证据交用户裁定。其他独立旅程可以继续，但该缺口不自动豁免，完整等价状态仍未完成。总纲不预批供应商付费实验、新依赖、对外部署或路线删减。

## 7. 跨项约束与需求覆盖

JSON 的九条跨项需求为：FR-002（完整清单）、FR-003（能力记录）、FR-004（固定参考）、FR-006（缺口不豁免）、FR-007（镜像与治理不变量）、FR-028（既有能力保留）、FR-029（真实验证）、FR-030（分批交付）、FR-031（独立审批和追踪）。其余 22 条需求由对应能力行归属，合计覆盖 FR-001..FR-031。

跨项要求仍须在有关子 change 的规格、任务与验证中兑现，而不是只在总纲出现一次：

- 拒绝、取消、失败和恢复与正常路径共同验收，未知形态、损坏流或无人值守 ask 继续 fail-closed。
- 控制授权与事件读取授权分别验证；远程默认不公开，重连不重复提交副作用。
- 保留缓存治理、费用估算、长期记忆、TUI 和可选 NATS 观察能力。费用估算不变成精确供应商账单，审计也不冒充 mulix 独有能力。
- 回放不执行历史工具；检索默认行为与索引范围必须公开，不能把单会话搜索写成全库搜索。
- 真实冒烟受环境阻塞时记录阻塞，不能用模拟用例、源码存在、静态配置或文档检查代替通过。

## 8. 能力记录与后续维护

`capabilities.json` 使用 `mulix.parity-roadmap.v1`，是本次初始规划索引，不是新的生产 Go API 或完整运行时能力服务。

- `planned_provider` 仅表示设计上的责任建议：`host`、`engine` 或 `joint`，不声称已验证提供方。
- 初始 `overall_status` 与各 `verification` 均为 `unverified`；`child_changes`、`reference_contracts`、`evidence` 为空，不填入尚未发生的批准或测试。
- 后续负责维护的独立 change 应建立参考契约的来源、输入/输出、失败/取消/恢复语义、默认配置及平台边界，记录受测 mulix 提交、CLI 版本和证据类型。
- 提供方、验证状态、交付进度彼此独立。状态可区分未验证、部分通过、通过与受约束不支持；后两者不能混算，未获批准的例外不能使整体通过。
- 实际 child ID 关联前核对其存在及范围；仅已创建不等于获批，仅归档不等于能力通过。跨会话介绍不是授权或运行证据。
- 初始验收脚本只适用于本次初始快照。后续状态演进须由相应 change 的新验证覆盖，不能将全部能力永久锁成 `unverified`，也不改写本次已批准计划来伪造历史 GREEN。
- JSON 结构需要演进时，由对应 change 明确兼容与版本处理；不把当前空数组解释成已批准的完整契约或证据格式。

后续可长期引用本文件、总纲 spec、任务计划和基线证据，不依赖被忽略的运行态设计稿。运行态 RED/GREEN、ledger 和评审资料保留本地；供长期复核的结论应在证据与阶段报告中持久化。

## 9. 共享 checkout 与完成语义

`.mulix/active` 是共享选择，不是会话私有锁。写任何产物或运行依赖 active 的脚本前确认 change 与 phase；先协调再切换，不用另一 change 的白名单写自己的文件。通过 `--change` 的独立状态命令不代替正确的产物写入阶段。

本次不新建 worktree。独立会话不代表文件系统隔离；共享 HEAD、index、active 仍须串行交接。只暂存本 change 文件，不改、reset、clean 或夹带其他会话与用户的未提交改动。

本总纲的 build/verify 完成，只表示“路线与追踪文档交付完成”。只有固定参考基线的全部批准契约通过、没有未经批准的例外，才可发布完整等价结论。总纲文档归档不能自动关闭未完成的产品目标；归档仍须用户另行决定。
